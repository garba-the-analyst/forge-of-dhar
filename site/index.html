Dhar. Bare Metal. Absolute Control.

A systems language built from scratch in Nigeria. It compiles straight to machine code: no libc, no runtime, no LLVM. It is early, and this page says exactly what works today and what does not.

What works today

Every line here was checked against the repositories and by running the compiler. Nothing on this board is a promise.

  • Works

    Stage 0 compiler

    dharc is written in NASM x86-64 assembly (nine modules, no libc). It reads a .dhar file and writes assembly; nasm and a linker turn that into a program. The conformance battery has 64 tests and all of them pass on both targets.

  • Works

    Native programs, no runtime

    Output is a small static program that talks to the operating system directly through sys. The examples below are about 9 KB each.

  • Works

    Bounds checking on buffers

    An index outside a raw[N] buffer stops the program with Dhar: index out of bounds and exit status 1, instead of silently corrupting memory.

  • Partly

    The language itself

    A strict first subset: i32, str, bool and raw[N]; tasks with parameters; give with a value or one operation (give a + b); when/shift/fallback; loops; sys calls; layout-only mold. Anything outside the subset is rejected with a clear message.

  • Works

    Target: Linux x86-64

    Programs are built, linked and run natively in the tests.

  • Partly

    Target: Windows x64

    Programs assemble as win64, link into a PE, and run correctly in a CPU emulator that checks the Windows calling rules; all 64 tests pass there. It has not been run on a real Windows machine yet, and dharc itself still runs only on Linux (on Windows, use WSL).

  • Not yet

    Targets: ARM64, RISC-V, WebAssembly (WASI)

    dharc refuses these with an error rather than producing the wrong output. They are planned as back ends of the Stage 1 compiler, on the machine-independent IR.

  • Designed

    Stage 1: the compiler written in Dhar

    8 source files exist in the Honing Dhar repository (lexer, parser, AST, symbols, type check, IR, code generation, driver) and all of them pass through Stage 0. They are scaffolding and stubs, not a working compiler.

  • Designed

    Safety without a garbage collector

    Compile-time ownership and borrowing (view, grab) and the error model (state, trap, enforce) are specified. Stage 0 rejects them; there is no borrow checker yet.

  • Designed

    Cybersecurity, AI and quantum direction

    The direction and its acceptance gates are written down (Canon Amendment A-1). Nothing for them is built yet: no std.crypto, no float or tensor types, no quantum back end.

  • Not yet

    Self-hosting

    Stage 1 does not compile itself, so the byte-for-byte bootstrap check has not been run.

  • Not yet

    Optimiser

    Every variable lives in memory and nothing is kept in registers. That is the main reason Dhar trails C in the speed test. Register allocation is planned for after the bootstrap.

  • Not yet

    Modules, standard library, Kun

    pull and expose are validated but link a single file. There is no importer, no standard library and no package manager yet; programs call the system directly.

  • Not yet

    Try Dhar in the browser

    Planned for this website. It needs a way to run dharc and the result in the browser, and nothing of that exists yet.

Checked 22 October 2026 against forge-of-dhar, last code change e429d85, and honing-dhar at commit cfa336b. This board is generated from one status file in the repository.

The language, as it runs now

Indentation scopes blocks. lock binds a value that cannot change; flux one that can. Each example below was compiled with the real dharc and run; the output beside it is what the program printed.

sys 1, 1, banner, 19 is the Linux write call: file 1 (standard output), the string, 19 bytes.

core.dhar
task core():
    lock banner: str = "System Initialized\n"
    flux counter: i32 = 0
    flux buffer: raw[256]

    span counter < 3:
        sys 1, 1, banner, 19
        counter = counter + 1

    lock done: str = "Limit reached\n"
    sys 1, 1, done, 14

when, shift and fallback are if, else if and else. A task takes typed parameters and is called by name.

branch.dhar
task classify(v: i32):
    when v == 1:
        lock a: str = "nominal\n"
        sys 1, 1, a, 8
    shift v == 2:
        lock b: str = "degraded\n"
        sys 1, 1, b, 9
    fallback:
        lock c: str = "unknown\n"
        sys 1, 1, c, 8

task core():
    classify(1)
    classify(2)
    classify(7)

Where Dhar is going

Security first, then AI, then quantum. None of this is built. It starts after Stage 1 compiles itself; until then the work is to leave room for it in the design. Each line below is a gate: a test that must pass before the line is called done.

1

Cybersecurity

Dhar already starts from the right place: no libc, no runtime, a compiler small enough to read, and bounds checks that stop an out-of-range write.

  • Partly

    S1 Memory safety floor. Every index is checked (this works today for raw[N]), and ownership and borrowing (view, grab) are enforced at compile time, with no garbage collector.

  • Not yet

    S2 Constant-time code. Values marked secret may not decide a branch or an array index, and the compiler may not rewrite them into one.

  • Not yet

    S3 A first std.crypto: SHA-256, ChaCha20-Poly1305, X25519 and Ed25519, each passing its published test vectors (FIPS 180-4, RFC 8439, RFC 7748, RFC 8032) and a timing test that shows no input-dependent variation.

  • Not yet

    S4 A build you can trust. Stage 1 compiles itself byte for byte, two machines produce identical output from the same source, and every build lists what went into it.

2

Artificial intelligence

Models are numbers in arrays. A language with checked bounds, no garbage collector and no runtime can run them with a memory use that is known before they start.

  • Not yet

    A1 Numbers for models: f32 and f64, fixed-point, and SIMD vector types, with results checked against a reference implementation.

  • Not yet

    A2 Tensors without a garbage collector: fixed-shape arrays and views with checked bounds, and arena allocation.

  • Not yet

    A3 Inference end to end: a small trained network (a handwritten-digit classifier) runs from a Dhar program with no outside runtime, and its outputs match a reference framework to a stated tolerance.

  • Not yet

    A4 Measured speed: the gap to optimised C on matrix multiply and on that network is published, whatever it is. GPUs and other accelerators come after this, not before.

3

Quantum computing

Two separate needs: protecting today's data from future quantum computers, which needs no quantum hardware, and describing and simulating quantum programs.

  • Not yet

    Q1 Post-quantum cryptography: ML-KEM (FIPS 203), ML-DSA (FIPS 204) and SLH-DSA (FIPS 205), each passing the NIST known-answer tests.

  • Not yet

    Q2 Circuits as data: a Dhar program builds a quantum circuit and writes it as OpenQASM 3 that a reference tool accepts.

  • Not yet

    Q3 A state-vector simulator written in Dhar, checked against a reference simulator on a fixed set of circuits.

  • Not yet

    Q4 Real quantum hardware stays out of scope until Q2 and Q3 pass and a provider's interface allows it.

The reasons, the design requirements being built into Stage 1 now, and the exact tests are in Canon Amendment A-1.

How Dhar becomes its own compiler

A new language cannot compile its own compiler on day one. Dhar follows the bootstrap blueprint: a small bridge first, then the real compiler written in Dhar, then the test that proves the bridge is no longer needed.

  1. 0

    Stage 0, the bridge Works

    Reads Dhar, writes assembly. The blueprint named C for the bridge; the one that exists is written directly in NASM assembly.

  2. 1

    Stage 1, the compiler in Dhar Designed

    The lexer, parser, type checker, IR and code generator, all written in Dhar itself and using only what Stage 0 accepts. Scaffolding exists; the compiler does not yet.

  3. 2

    Hand-off Not yet

    Stage 0 compiles the Stage 1 source. The result is the first compiler built from Dhar's own code.

  4. 3

    Self-host check Not yet

    That compiler compiles the Stage 1 source again. If the logic is sound, the two executables are byte-for-byte identical.

  5. 4

    Independence Not yet

    Stage 0 is archived. After that, optimisation, a standard library and tooling are built on Dhar itself.

Where the design is heading

One front end and a machine-independent middle, with a small back end per processor. Today Stage 0 goes straight from source to x86-64 and skips the middle.

Speed, measured and not flattered

One small workload, run the same way in eight languages. The honest summary: Dhar is far ahead of the runtimes and well behind optimised C.

  • The workload scans 1,048,576 values for spaces and newlines (16 × 65,536 steps), with the same branches in every language. It is one test, not a verdict on everything.
  • Each figure is 100 runs after 3 warm-ups with hyperfine, pinned to one core. It is whole-process time, so Node, Java, PHP and Python include their start-up.
  • At a millisecond or two, start-up and scheduler noise are as large as the work. The spread is as big as the mean for several entries, so the median is the steadier figure.
  • The gap to C is expected. Stage 0 keeps every variable in memory and does no optimisation, while GCC vectorises this loop.
  • An earlier result that had Dhar beating C came from a code-generation bug (loops that never ran). It was withdrawn and the test rerun.

A name from deep time

Dhar comes from the pre-Islamic Arabic dahr: time without bound, eternity, and the fate that runs through it. It is a name for something meant to last. It does not mean "absolution", a common mix-up.

The package manager is Kun, from the Arabic command kun, "be" (as in kun fa-yakun, "be, and it is").
